# AttendX V1.1.9.1 — Protected Institution Identity

> Local development patch. Not pushed or published.

V1.1.9.1 adds a secure institution-branding workspace without expanding the V1.1.9 class-management scope. It is intended as a maintenance patch for service-operated deployments.

## Included changes

- Admin++ can update the institution name, short code, campus, primary logo, and optional secondary logo from Settings.
- Every mutation requires the existing session-bound Admin++ password elevation plus the exact `UPDATE BRANDING` phrase.
- The primary logo is always present through a database asset or safe bundled fallback and is used for the sidebar, login, logout, password centre, dashboard watermark, live preview, and favicon by default.
- Admin++ may upload an optional dedicated favicon that overrides only the browser-tab icon. Removing the override immediately returns favicon behavior to the primary logo.
- The secondary logo is optional. JSX does not render its container when disabled, so layouts remain balanced without empty spacing.
- Saved branding is delivered through a public read-only endpoint so the login page can display it before authentication.
- Changes update the active React tree, document title, favicon, CSS watermark variable, and workbook company/footer metadata immediately after the server confirms the transaction.

## Upload protection

- Only `.png`, `.jpg`, and `.jpeg` logos are selectable and accepted.
- Client and server both enforce MIME and extension checks.
- Server validation inspects PNG/JPEG magic bytes and structure rather than trusting browser metadata.
- Logos are limited to 2 MB each, 32–4096 pixels per side, and 12 megapixels.
- Each request accepts at most one primary and one secondary logo with bounded multipart fields and parts.
- Branding uploads are limited to five attempts per Admin++ account per 15 minutes.
- A server-enforced, cancellable ten-second upload window shows Upload, Signature, Dimensions, and Apply stages with progress and ETA; disconnecting before completion prevents the database commit.
- Branding text and assets are written atomically; audit history stores metadata only, never image bytes or passwords.
- Logo responses use `nosniff`, checksum ETags, immutable cache URLs, and explicit content types.

## Backup restore hardening

- The browser picker now allows `.sqlite` files only.
- Client preflight validates size and the `SQLite format 3` signature.
- Server filtering validates extension and allowed SQLite MIME values.
- Restore uploads stream to a uniquely named staged file instead of allocating the full backup in process memory.
- The server re-checks the SQLite signature, integrity, schema, ownership, foreign keys, and active administrator before replacement.
- Restore upload attempts are limited to three per Admin++ account per 15 minutes.
- Failed staging removes the temporary file.

## Password-manager boundary

- Login intentionally keeps `autocomplete="username"` and `autocomplete="current-password"` so users can save and retrieve their normal sign-in there.
- Every password or confirmation field outside Login uses the shared manual-entry control.
- Protected inputs expose no visible credential field name, use a neutral generated DOM identifier and `one-time-code` autocomplete semantics, and mark themselves ignored for common password managers.
- Inputs remain read-only until deliberately focused and reject paste/drop while still accepting normal keyboard entry reliably.
- A hidden non-password form bridge submits the manually typed value to existing handlers without exposing the visible control as a savable account credential.

## Database change

Migration `012-institution-branding` adds `branding_assets`, keyed by `PRIMARY` or `SECONDARY`, with content type, original filename, byte size, dimensions, SHA-256 checksum, binary data, and timestamps. Storing assets in the application database means normal AttendX backups and restores retain the complete institution identity.

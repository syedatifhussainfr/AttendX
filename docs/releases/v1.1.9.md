# AttendX V1.1.9 — Database-Backed Class Workspaces

V1.1.9 expands AttendX from a single operational class into a database-backed academic workspace system. Administrators can create and manage multiple classes, assign mentors, faculty, and class representatives, organize course subjects, and keep each class's roster, timetable, attendance, analytics, history, and exports isolated.

This is an in-place upgrade from V1.1.8. It does not contain deployment databases, student rosters, attendance exports, backups, credentials, local configuration, or institution-specific operational data.

## Highlights

- Database-defined classes with display name, unique class code, course, specialization, semester, section, academic year, batch, mentor, and active state.
- A searchable workspace switcher designed for large class catalogues, with keyboard support, contained scrolling, responsive mobile behavior, and a restrained glass interface.
- Class-scoped students, timetable entries, attendance sessions, history, dashboard metrics, analytics, reports, and exports.
- Per-class roll-number uniqueness, allowing the same roll number in different classes while preventing duplicates within one class.
- Course-organized subject catalogue with explicit subject-to-class assignment.
- New `FACULTY` role with Mentor, Faculty, and CR class assignments.
- Assigned faculty can operate their class workspace without receiving global database, backup, user-role, settings, or Admin++ authority.
- ADMIN retains institution-wide visibility and class management; Admin++ retains archive and guarded permanent deletion authority.
- Password-confirmed class deletion and staff unassignment with typed confirmation phrases, server-side credential verification, and audit records.
- Neutral glass class-management interface with structured metadata, statistics, subject groups, staff responsibilities, responsive layouts, and non-destructive selection states.
- Startup waits for API health before launching the web interface, preventing the initial session or login request from racing backend initialization.

## Database migrations

Migrations run automatically and are idempotent.

### `008-academic-classes`

- Creates class workspace, staff-assignment, and class-subject assignment structures.
- Adds the initial database-backed academic workspace records.
- Introduces the `FACULTY` role and class responsibility model.

### `009-class-ownership`

- Assigns existing students, timetable entries, sessions, subjects, and relevant access to the migrated class workspace.
- Replaces the legacy global roll-number uniqueness rule with a per-class composite constraint.

### `010-attendance-record-ownership`

- Preserves attendance-to-student ownership during roster-table reconstruction.
- Rejects attendance rows whose student and session belong to different classes.

### `011-subject-course-category`

- Adds course categorization to the subject catalogue.
- Categorizes the migrated subject catalogue for the initial BCA workspaces.

Existing V1.1.8 operational records migrate to `ANASUYA BCA AI 3B.UG`; the initial A, B, and C workspaces are stored as database rows and can be renamed or replaced through class management. They are not hardcoded frontend choices.

## Roles and class authority

| Capability | CR | FACULTY | ADMIN | ADMIN++ |
| --- | :---: | :---: | :---: | :---: |
| View assigned class | ✓ | ✓ | All | All |
| Run attendance | ✓ | ✓ | ✓ | ✓ |
| Manage assigned roster, subjects, and timetable | Policy controlled | ✓ | ✓ | ✓ |
| Correct/reopen closed attendance | — | Assigned classes | ✓ | ✓ |
| Create and edit class workspaces | — | Assigned scope | ✓ | ✓ |
| Assign class staff and subjects | — | Assigned scope | ✓ | ✓ |
| Archive or permanently delete a class | — | — | — | ✓ |
| Access global users, settings, database, or backups | — | — | Role dependent | ✓ |

Admin++ remains a CLI-controlled authority. It cannot be granted through the browser or configuration file. Protected privilege ceilings prevent FACULTY, ADMIN, or CR policy changes from acquiring destructive Admin++ operations.

## Protected destructive operations

- A class containing students, timetable entries, or attendance history cannot be permanently deleted; archive it to preserve relationships.
- Empty-class deletion requires the exact `DELETE CLASS` phrase and the current Admin++ password.
- Staff unassignment requires the exact `REMOVE ACCESS` phrase and the current operator password.
- Protected fields reject clipboard paste and drop so confirmation remains deliberate.
- Credential verification happens on the server; passwords and confirmation values are not persisted in browser storage.
- Existing self-lockout, last-Admin++, relationship, audit, and historical-retention protections remain active.

## Upgrade from V1.1.8

Create and retain a tested backup before updating:

```bash
npm run backup
git pull origin main
npm install
npm run config-check
npm run doctor
npm run dev
```

After upgrading:

1. Sign in as Admin++ and review **Classes**.
2. Confirm migrated students, timetable entries, attendance history, and subjects appear under the intended class.
3. Review Mentor, Faculty, and CR assignments for every class.
4. Check that class subjects match its course and timetable.
5. Open representative student profiles and compare totals with a review export.
6. Verify FACULTY and CR accounts cannot enter global protected areas.
7. Rehearse backup restoration on a disposable copy before production rollout.
8. Keep the pre-upgrade backup until a complete attendance cycle and export review have passed.

No roster re-import is required. Do not manually edit migration records or copy a live SQLite file while the API is running.

## Security and privacy

- Class scope is enforced in backend queries rather than trusted from frontend navigation state.
- Faculty authorization is tied to active class assignments.
- Attendance records must retain both a valid student owner and session owner in the same class.
- Student private fields remain restricted at the API boundary.
- Password and refresh-token hashes remain redacted from the read-only database browser.
- Access tokens remain short-lived and memory-only; refresh tokens remain hashed, rotated, cookie-restricted, and revocable.
- Local databases, journals, backups, configuration overrides, environment files, exports, uploads, logs, and recovery archives remain excluded from Git.

## Compatibility and scope

- Node.js 20 or newer remains required.
- SQLite remains the primary local deployment database; application-level PostgreSQL configuration remains supported.
- V1.1.9 supports multiple class workspaces inside one isolated institution deployment.
- It does not introduce shared multi-tenant isolation, subscriptions, billing, customer self-provisioning, or a central operator control plane.
- Each institution should continue to use an isolated application deployment and database.

## Rollback

Database migrations add and rebuild ownership structures, so application rollback must use the pre-upgrade database backup:

1. Stop AttendX.
2. Preserve the current V1.1.9 database separately for investigation.
3. Check out the previous release: `git checkout v1.1.8`.
4. Install that release's dependencies with `npm install`.
5. Restore the tested V1.1.8 backup using the documented restore workflow.
6. Run `npm run doctor` before reopening access.

Do not run V1.1.8 code against a database already migrated and actively used by V1.1.9.
